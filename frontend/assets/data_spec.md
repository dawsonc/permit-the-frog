# Frontend data spec

What the pipeline emits for the one-page app, and why each piece exists.

The page is static: no backend, no query API. Everything it needs ships as flat
files next to `index.html`, loaded once and filtered in memory. This document is
the contract between `scripts/process_somerville_data.py` and `frontend/app.js`.

**Permit rows are not tied to addresses.** The source data is public, but
republishing a browsable "what your neighbours paid, by address" table is a
different act from the city publishing a permit log. The page answers *"what do
people with a house like yours pay?"* — matching on assessor property metadata,
never on identity of place. §5 covers what that costs and what it takes to hold.

All counts below are measured against the current extract
(`data/processed/ma/somerville/joined_data.csv`, permits through 2026-09-03).

---

## 1. Files

Two files, plus a small manifest:

| File | Size (gzipped) | When loaded | Purpose |
|---|---|---|---|
| `meta.json` | ~2 KB | immediately | Headline numbers, facet value lists, build provenance |
| `permits.json` | ~0.53 MB | immediately | The table. Every tagged permit, de-identified |
| `addresses.json` | ~130 KB | on first focus of the address box | Every address in the city, permits or not |

`meta.json` is separate so the page can paint the headline and build the filter
controls before the main payload lands. `addresses.json` is deferred because the
address box is a convenience, not the primary path — most visitors will never
focus it, and deferring it is a one-line `fetch` on the `focus` event.

**The two data files share no join key.** That is the whole design (§5).
`addresses.json` turns the visitor's own address into property attributes;
`permits.json` is filtered by those attributes. Nothing in either file maps a
permit back to a place.

Everything is generated by `make process-somerville` and written to
`frontend/data/`. The files are build artifacts; `data/` is gitignored, so decide
whether these get committed — they are small enough to, and it makes deployment a
folder copy.

## 2. `permits.json`

### Format

Array-of-arrays with a column header, not an array of objects:

```json
{
  "cols": ["date", "trade", "desc", "cost", "..."],
  "rows": [
    ["2021-04", "Electrical Permit", "Wire 48k btu ductless mini-split", 4200, ...],
    ...
  ]
}
```

Records-style JSON repeats every key on all 13,107 rows and roughly doubles the
raw size. Gzipped the gap is smaller, but raw size is what the browser parses and
holds, and `{cols, rows}` costs about five lines to index:

```js
const idx = Object.fromEntries(data.cols.map((c, i) => [c, i]));
const cost = row[idx.cost];
```

Raw CSV is marginally smaller again but needs a real parser — descriptions
contain commas, quotes and newlines — so JSON wins on complexity.

### Population

One row per **tagged** permit: residential, in the four trade families, with at
least one project-type flag set. **13,107 rows** of the 62,050 residential
permits. Untagged permits (`renovation`, `rewire 3 units`, ...) are dropped —
they carry no equipment signal, so the page can say nothing about them.

Rows are **shuffled** before writing. Source order is chronological within
parcel, which leaks adjacency: consecutive rows sharing a property profile are
usually the same building.

### Columns

| Column | Type | Null | Notes |
|---|---|---|---|
| `date` | string | 0% | `YYYY-MM`. Day precision isn't used by any control, sorts lexically, and is one fewer correlating field |
| `trade` | string | 0% | `Electrical Permit` 6,247 / `Gas Fitting` 3,349 / `Building Permit` 2,441 / `Plumbing Permit` 1,070 |
| `status` | string | 0% | **New — not in the pipeline.** See §4 |
| `desc` | string | 0% | `project_description`, truncated to 200 chars **and address-scrubbed**. See §4 |
| `cost` | number \| null | 34% | **New — not in the pipeline.** See §4 |
| `hp` `panel` `solar` `ev` `hvac` | 0 \| 1 | 0% | The five project-type flags, independent — a row can set several |
| `kw` | number \| null | — | Solar capacity parsed from `desc`. See §4 |
| `zones` | number \| null | — | Heat pump indoor-unit count parsed from `desc`. See §4 |
| `hood` | string \| null | 3% | **New.** `Application Neighborhood` — 17 values, `Spring Hill` 2,281, `Union Square` 1,786, `Davis Square` 1,600. The coarsest useful "near me" signal |
| `contractor` | string \| null | 1.3% | `contractor_company_name` falling back to `applicant_company_name` — Gas Fitting and Plumbing never populate the former. 3,060 distinct firms. A business, not a resident |
| `year_built` | number \| null | 1.0% | **Rounded to the decade.** Range 1710–2020, median decade 1900 |
| `res_area` | number \| null | 0.8% | **Rounded to 500 sq ft.** Median ~2,500. Whole-building sum when `attr_level` is `parcel` |
| `stories` | number \| null | 26% | Free text in CAMA, happens to be clean decimals. Heavy nulls — do not make it a required filter |
| `style` | string \| null | 0.7% | Display only. 60 distinct values, uncollapsed. See §6 |
| `prop_class` | string \| null | 0.7% | Derived from `use_code`. **The property-type filter facet.** See §4 |
| `attr_level` | `unit` \| `parcel` \| null | — | Provenance of the property attributes: 11,746 unit / 1,266 parcel / 95 unmatched. Whether `res_area` is one dwelling or a whole building |

### Deliberately excluded

| Field | Why |
|---|---|
| `address` | The point. Was ~450 KB raw anyway |
| `parcel_prefix` | Joins straight to `addresses.json` and reconstitutes the address column exactly. **Shipping this would undo everything else in this section** |
| `latitude` / `longitude` | Exact coordinates are the address |
| `application_number` | The city's portal is keyed on it and publishes the address. A trivially joinable public key defeats the rest. Use the array index as the row key |
| `Application Block Code` | 567 census blocks over ~13k buildings — a handful of homes each |
| `Application Precinct` | 28 values. Probably fine, but `hood` already covers locality and this adds a second, finer geography to cross |
| `apn`, `loc_id`, `prop_id` | Parcel identifiers by another name |
| `units` | Dead field — see §6 |

### Size

| Variant | Rows | Raw | Gzipped |
|---|---|---|---|
| **De-identified, as specced** | **13,107** | **3.19 MB** | **0.53 MB** |
| With `addr` + `parcel` + `id` | 13,107 | 4.24 MB | 0.92 MB |
| De-identified, cost present only | 8,688 | ~2.1 MB | ~0.35 MB |

Dropping the identifying columns nearly halves the payload — the address strings
and their per-row keys were the least compressible thing in the file.

**Ship all 13,107 rows.** Restricting to rows with a cost saves ~0.18 MB and
makes the file unable to answer "has anyone done this at all?", and the dropped
rows are almost entirely `hvac` — the category the page is least about. Have the
UI hide cost-less rows by default behind a toggle instead.

## 3. `addresses.json`

Same `{cols, rows}` shape. One row per **building**, from the assessor table —
not from the permits — so an address with no permit history still resolves.

**13,027 distinct addresses** across 681 streets, rolled up from 19,013
unit-level assessor rows.

| Column | Notes |
|---|---|
| `addr` | Display form, e.g. `46 LAUREL ST` |
| `norm` | Normalized match target. See below |
| `year_built` `res_area` `stories` `prop_class` | **Bucketed identically to `permits.json`** — decade, 500 sq ft. They are compared against those columns, so they must be on the same grid |

There is **no parcel key**. The attributes ride on the address row directly, so
the file has nothing to join a permit to.

This file is a lookup table the visitor searches, not a list the page displays.
It is every address in a public assessor database, published as-is; the change
from the status quo is that it is no longer wired to anything.

### What selecting an address does

It reads the property attributes and **sets the filters** — "houses like yours" —
then throws the address away. It does not filter the table to that address; there
is no column to filter on. This is also what makes the box work for the ~2,500
addresses with no permits at all, which was the original reason to build it from
assessor data rather than from the permit rows.

### Normalization

`SITE_ADDR` is not clean, and `norm` exists so search never touches the display
string:

- **2,711 rows have double spaces** (`0  BOSTON AVE`) — collapse whitespace
- **Condo rollups keep unit suffixes** (`16 WATERHOUSE ST #1`, `129 BOSTON AVE #129A`) — strip from `#` onward for the building-level label
- **97 rows are `ADDR_NUM == '0'`**, plus rows with no number at all (`SHORE DR`) — vacant parcels and paper streets. Exclude from the file
- **Everything is abbreviated**: `ST` 11,479, `AVE` 4,318, `RD` 1,290, then `TERR` `PL` `BLVD` `CT` `PKWY` `HWY`. Someone typing "Main Street" matches nothing against `MAIN ST` under any matcher, fuzzy or not. Apply one suffix map (`street→st`, `avenue→ave`, `road→rd`, `parkway→pkwy`, `terrace→terr`, `boulevard→blvd`, `place→pl`, `court→ct`, `highway→hwy`) to both `norm` and the query, lowercase both, collapse whitespace

## 4. New pipeline work

### `cost` — required, blocking

`Estimated Construction Cost` (raw column 26) is not in `PERMIT_COLS`
(`scripts/process_somerville_data.py:36`). The entire page is about price.

Strip `$` and `,`, coerce to numeric. Coverage is **entirely determined by
trade**, which is worth stating on the page rather than hiding:

| Trade | Rows | With cost |
|---|---|---|
| Building Permit | 2,441 | 100% |
| Electrical Permit | 6,247 | 100% |
| Gas Fitting | 3,349 | **0%** |
| Plumbing Permit | 1,070 | **0%** |

The four headline categories are unaffected — heat pumps 99.3%, panels 99.9%,
solar 99.8%, EV chargers 100%. Only `hvac` suffers (26.7%), because it is 3,342
Gas Fitting and 1,058 Plumbing rows that structurally never carry a price.

Distribution across tagged rows with a cost: p25 $2,000, median $8,000, p75
$23,691, p95 $97,201, max $9,997,000. **27 rows are exactly 0** and 79 exceed
$500k. Emit as-is and let the UI clamp — do not silently drop outliers in the
pipeline.

### `desc` address scrub — required

**143 tagged descriptions (1.1%) contain a street address in free text**, which
dropping the `addr` column does not fix:

```
@65 Irving St
Wire (1) condenser, and (1) Air Handler Unit @ 103 Raymond Ave
Electric panel replacement on 75 myrtle street
water heater/boiler 13 Lesley Ave
```

Redact `\d+\s*-?\s*\d*\s+[A-Za-z]+\s+(st|street|ave|avenue|rd|road|pl|place|terr|
ct|way|sq|...)\b` to `[address]` before truncating. Match the street-suffix list
to the 681 real street names rather than guessing — it is a small file and a
literal alternation is both faster and more precise than a general pattern.

This regex is the weakest link in §5 and should get a test: assert zero matches
in the emitted file.

### `status` — required

Raw column 6, currently unused. 470 Withdrawn and 246 Denied permits sit in the
tagged set. A denied permit's estimated cost was never a real transaction, so
these must be excludable. Ship the raw string; default the UI to `Closed` +
`Issued` (11,922 rows).

### `kw` — solar capacity

Now in dataset

### `zones` — heat pump size proxy

Now in dataset

### `prop_class` — property type facet

Map the MA state class code in `use_code` (first three digits) to a label:

| Code | Label | Rows |
|---|---|---|
| 101 | Single family | 2,900 |
| 102 | Condominium | 3,253 |
| 104 | Two-family | 4,245 |
| 105 | Three-family | 1,612 |
| 109 | Multiple houses on one parcel | 71 |
| 111, 112 | Apartments | 537 |
| other | Other / mixed use | ~394 |

This is the clean facet, and it makes normalizing `style` unnecessary (§6).

### Bucketing — required

Round `year_built` to the decade and `res_area` to 500 sq ft, in the pipeline,
before writing either file. Reasons in §5. Both files must use the same grid or
address lookup silently stops matching. Make bucket widths easy-to-change constants

## 5. What "no addresses" actually requires

Dropping the address column is the easy part. Three things have to hold with it.

**No join key, in either file.** `parcel_prefix` in `permits.json` plus
`addresses.json` reconstructs the address column exactly, in about four lines of
JavaScript, for anyone who opens devtools. Same for lat/lon and for
`application_number`, which the city's own portal resolves to an address. These
are listed as excluded in §2 because each individually undoes the whole thing.

**Free text is a leak.** 143 descriptions name an address outright (§4).

**Property attributes are a quasi-identifier.** Measured on the tagged set:

| Fields | Distinct combinations | Rows in a group of one |
|---|---|---|
| `year_built` + `res_area`, raw | 5,145 | **1,812** |
| + `prop_class` | 5,562 | **2,118** |
| decade + 500 sq ft bucket | 339 | **78** |

Exact assessor values are close to a fingerprint: 1,812 tagged permits sit on a
(year, area) pair shared with no other permit, and Somerville has only ~13k
buildings, so a reader holding the assessor file — public, and shipped in
`addresses.json` — can often name the property. Bucketing to decade and 500 sq ft
cuts that to 78 rows and costs the UI nothing, because the filters were going to
be coarse ranges regardless.

The 78 residual singletons are mostly genuinely unusual buildings. Worth a look
before launch; suppressing `res_area` on rows in a bucket of one is a two-line
fix if it matters.

**Residual risk, accepted:** `hood` × `date` × `contractor` still narrows things
for a small firm working one street in one month. Locality is most of what makes
the table feel real, and neighborhood is the coarsest geography that still does.
Flagging it, not fixing it — if it needs tightening later, coarsen `date` to the
quarter first, since it's the cheapest of the three to give up.

**What this costs the product.** "Has anyone on my street done this?" is no
longer answerable — only "anyone in Spring Hill, in a 1900s two-family of about
2,500 sq ft." That is the weaker claim, and the page should make it in those
words rather than implying address-level precision it deliberately doesn't have.

## 6. Fields deliberately excluded

**`units` is dead.** 12,942 of 13,009 non-null values are `0` — the assessor's
`UNITS` column is simply not populated in Somerville. It cannot be a filter and
should not appear in the UI. (Unit count is recoverable from `prop_class`, which
is what the state class codes encode.)

**`style` is display-only, not a facet.** 60 distinct values with heavy
duplication — `Two Family` (3,278), `2 Fam Conv` (1,112), `2-Decker` (863),
`Two decker` (283) are one building type spelled four ways; likewise
`3 fam Conv` / `3-Decker` / `Three decker` / `3-Decker-Apts`. Collapsing them is
real work that `prop_class` already does correctly from a coded field. Show
`style` in the table because it is evocative ("Mansard", "Cottage Bungalow");
don't filter on it.

## 7. `meta.json`

Small, hand-shaped, loaded first:

```json
{
  "generated": "2026-09-06",
  "permit_extract": "2026_09_03",
  "assessor_vintage": "CY25_FY25",
  "date_range": ["2014-02", "2026-09"],
  "n_permits": 13107,
  "n_addresses": 13027,
  "headline": {
    "solar":  {"label": "Rooftop solar", "value": 4418, "unit": "/kW", "n": 2007},
    "hp":     {"label": "Heat pumps",    "value": 6018, "unit": "",    "n": 1474},
    "panel":  {"label": "Panel upgrade", "value": 5000, "unit": "",    "n": 3380}
  },
  "facets": {
    "prop_class": ["Single family", "Condominium", "..."],
    "hood": ["Spring Hill", "Union Square", "..."],
    "trade": ["Building Permit", "..."],
    "status": ["Closed", "Issued", "..."]
  }
}
```

The `headline` block is the page-load default. Once `permits.json` is in memory
the cards should **recompute from the currently filtered rows** — same code path
as the table, and it makes the filters visibly do something. `n` is carried so a
card can grey out when a filter narrows it to too few permits to be meaningful.

## 8. Generation

One new flag on the existing script, one new Makefile target:

```
uv run python scripts/process_somerville_data.py --frontend-out frontend/data/
```

Writes all three files. The joined CSV stays as-is — it is the analysis artifact,
it keeps addresses and parcel keys, and the notebooks read it. The frontend files
are a de-identified projection of it plus the assessor address rollup, which the
script already loads for the parcel join.

**The de-identification lives in this step, not upstream.** Ship a test that
opens the emitted `permits.json` and asserts: no column named `addr`, `parcel`,
`lat`, `lon`, or `id`; zero descriptions matching the address pattern;
`year_built % 10 == 0` and `res_area % 500 == 0` throughout. It is a dozen lines
and it is what keeps a later "just add parcel_prefix, it's useful for debugging"
from quietly undoing §5.
